# Anti-Gravity OS v4 — Phase 6 Core Asset Audit

**Status:** batch 1 decision record; source revisions limited to the Studio router and two core routes  
**Date:** 2026-08-18  
**Scope:** canonical skill and workflow classification before selective refactoring  
**Authority:** this record does not authorize installation, publication, external effects, deletion, or a broad rewrite.

## 1. The decision

The current registry has **71 skill entries** and **52 workflow entries**. That is an inventory count, not a claim that Anti-Gravity should expose 71 independent expert personalities on an ordinary task.

V4 keeps a capability only when it adds reusable judgement, a bounded operating procedure, or a resource that a capable general model would not reliably select on its own. It moves a narrow helper, command recipe, scanner, or selection library out of the "general expert" mental model without deleting useful material.

The first General payload remains intentionally small: **29 current entries**, of which several are already labelled `procedure` or `tool_adapter` in the manifest. The following batches will reduce routine discovery further by making that distinction visible in the router and host payloads; they will not delete content merely to achieve an attractive number.

**Size is not a quality metric.** A long skill remains long when its examples, critique language, specialist judgement, or references materially improve the result. `deep-think`, `master-design-director`, and any similarly intentional package are protected from mechanical compression. A proposed reduction must name the exact material being moved or removed, its destination, and a positive/negative behaviour test that shows the capability was preserved or improved.

## 2. Classification rules

| Class | Meaning | Exposure rule |
| --- | --- | --- |
| Capability | Reusable judgement that materially improves a class of decisions | May be selected from a relevant functional boundary. |
| Route | A risk-sized task path that coordinates one or more capabilities | Select only when it improves the task over direct execution. |
| Procedure | A narrow, optional method or command sequence | Load only on a named or clearly matched need. |
| Tool adapter | Guidance for a specific scanner, host surface, or setup action | Never treat a passing tool result as complete assurance. |
| Reference/recipe | Deep examples, patterns, or a lookup library | Load after the decision/job is named; never as always-on policy. |
| Candidate for merge/retirement | Overlapping, stale, or incorrectly shaped material | Preserve until the targeted audit supplies a safe destination and behaviour test. |

## 5. Why Motion Library stays

`motion-library` is not noise. Its job is to make a previously chosen motion intention concrete: it lets an agent find a suitable pattern without inventing an effect from scratch. V4 retains that behaviour with three boundaries:

1. Activate it only after the request or Design Direction has named the interaction, narrative, or communication job.
2. Return a small set of candidates with accessibility, performance, and fallback implications.
3. Do not let the library choose the story, visual system, or implementation architecture.

This preserves the exact reason Beloved created it while preventing it from adding irrelevant context to ordinary UI or engineering work.

## 6. Canva CI candidate

There is no canonical `canva-ci` asset in the current manifest. It is therefore neither missing from General nor silently discarded. When Beloved supplies the actual source or desired behaviour, it will receive this audit card before admission:

1. What repeatable decision or verification does it add beyond `ui-ux`, `design-ui`, and a general visual review?
2. Is it a Canva-specific tool adapter, a portable brand-system capability, or a conditional reference package?
3. What host/tool access does it assume, and what is the graceful fallback without that access?
4. What example proves it improves a design outcome rather than merely adds a brand checklist?

## 7. Audit card required before every future source edit

| Question | Required answer |
| --- | --- |
| Unique value | What decision/result improves beyond ordinary model capability? |
| Activation | What exact signals activate it, and what neighbouring tasks exclude it? |
| Durability | Which guidance is portable versus provider-, stack-, date-, or project-specific? |
| Correct home | Capability, route, procedure, tool adapter, reference/recipe, merge, or retirement candidate? |
| Behaviour proof | What positive and negative task demonstrates that the revised asset improves selection or output? |
| Preservation proof | If anything is compressed, merged, or moved, what exact content is retained where, and what test proves no useful judgement was lost? |

## 8. Batch 1 implemented scope

This batch changes only the assets whose job is selection and project framing:

- `global/GLOBAL_MEMORY.md` becomes a compact Studio Director router.
- `workflow-task-dispatch.md` becomes an optional bounded-delegation route, rather than a background assumption that work should be split.
- `workflow-project-inception.md` becomes a proportional product-framing route, rather than a mandatory waterfall that forces design, stack selection, memory, and build steps on every new idea.
