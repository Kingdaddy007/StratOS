# Fault-class map

Load this reference after the initial evidence pass identifies a relevant fault class. It is a way to choose discriminating checks, not a replacement for causal reasoning.

| Fault class | First checks | Stronger evidence pattern | False-positive risk | Default boundary |
| --- | --- | --- | --- | --- |
| Logic or contract | Small input, pre/postconditions, function/API boundaries, first invalid state. | A contract violation predicts the symptom and a targeted regression catches it. | Patching the final exception instead of the upstream invalid transition. | Diagnose/propose; local repair when authorized. |
| Misleading stack trace | Trace callers, data lineage, and earliest invalid value or branch. | Upstream divergence explains the downstream crash. | Treating file/line in the trace as the cause. | Read-only until the mechanism is established. |
| Configuration or environment | Effective runtime values, flags, versions, deployment/runtime shape, known-good comparison. | Behavior changes with controlled environment/configuration difference while code is held constant. | Editing code to compensate for runtime configuration. | Propose; configuration/deployment mutation needs approval. |
| Dependency, build, or commit | Lockfile, transitive versions, compiler/runtime, generated output, ordered change history. | A reliable comparison identifies a change point and mechanism. | Treating the first bad commit as sufficient root-cause proof. | Diagnose/propose. |
| State, cache, or persistence | State transitions, transactions, serialization, cache key/TTL/invalidation, retry/idempotency. | Cold/warm state, snapshot, or replay isolates the divergent transition. | Clearing cache or resetting data as a cosmetic cure. | No state mutation by default; data repair needs approval. |
| API, integration, or third party | Request/response, schema/version, auth scope, retries, timeout, provider status, clock. | Boundary exchange and local behavior jointly explain failure. | Blaming provider without checking request construction or local resilience. | Propose; incident route if impact is material. |
| Concurrency, timing, or flaky behavior | Repetition, ordering, clocks, contention, async boundaries, isolated scheduling/load. | Failure rate or invariant changes with controlled interleaving. | Adding sleeps, skipping a test, or treating one rerun as proof. | Diagnose first; avoid speculative timing edits. |
| UI or client state | Exact route, session, permissions, persisted storage, network sequence, DOM/state transition. | Client state/event ordering diverges from the contract in affected context. | CSS or backend fix that hides stale client state. | Low-risk local repair only with visual and functional checks. |
| Performance or resources | Baseline, threshold, representative workload, trace/metric correlation, query/queue/payload behavior. | Controlled load identifies a bottleneck and links it to the symptom. | Optimizing a correlated metric without causal evidence. | Propose; production tuning needs approval. |
| Data integrity, authorization, or security | Preserve evidence, scope impact, inspect invariants/audit data, classify access and reversibility. | Independent invariant or controlled reconstruction supports a causal chain. | Deleting evidence, exposing data, weakening authorization, or repairing records speculatively. | Read-only; human approval for recovery or disclosure. |
| No code change justified | Contract/oracle, environment, operator action, quota/certificate, third party, and evidence adequacy. | The reported expectation is wrong, mechanism is external, or evidence cannot support a safe edit. | Inventing a code defect to look useful. | Stop/escalate or propose a non-code owner action. |
