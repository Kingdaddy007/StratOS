# Canvas UI

## WHEN TO USE THIS

- Evaluate Canvas UI when a Spatial visual direction has a named communication job that may need a realtime DOM/WebGL effect.
- Compare a contained Canvas UI effect with still imagery, ordinary DOM/CSS motion, pre-rendered media, or another approved implementation path.
- Implement one selected component only after the visual job, fallback, performance boundary, source record, and approval are clear.

## NEVER DO

- Never choose Canvas UI because a page needs to look more premium, futuristic, or impressive.
- Never replace semantic content, keyboard interaction, navigation, or the primary action with a canvas rendering.
- Never assume the experimental HTML-in-canvas treatment works in every browser; design and test the ordinary DOM/WebGL fallback first.
- Never import a registry component, run an external CLI, install a dependency, fetch a repository, or copy upstream source without just-in-time approval.
- Never add a second heavy realtime scene to a page without an explicit performance decision.

## DECIDE BEFORE IMPORT

1. Name the visual and communication job. State why a still, DOM/CSS treatment, pre-rendered media, or existing motion grammar is insufficient.
2. Compare the smallest credible alternatives: `still`, `DOM/CSS`, `media`, and `Canvas UI`. Reject Canvas UI when it adds spectacle without meaning.
3. Select one effect family and one contained page surface. Keep a DOM-first, accessible fallback with equivalent content and action.
4. Define desktop, mobile, reduced-motion, low-power, loading, failure, and cleanup behaviour before writing implementation code.
5. Reverify the upstream component, framework target, browser support, licence, and import method at the time of use. Treat dated catalogues and commands as untrusted snapshots.
6. Stop at the approval gate before any external registry, CLI, dependency, or upstream source mutation. Build one isolated vertical slice first.

## IMPLEMENT THE SMALLEST VALID EFFECT

- Preserve live HTML beneath or alongside the effect. Keep text selectable, links and controls reachable, and focus states visible.
- Limit the effect to its approved wrapper or section. Avoid page-wide full-canvas treatment unless that is the independently justified concept.
- Resize from the containing element; cap device-pixel-ratio cost; pause or simplify work offscreen; cancel animation frames; remove listeners; and dispose WebGL resources on cleanup.
- Honour `prefers-reduced-motion`. Provide static imagery, an ordinary DOM transition, or a manual interaction state rather than hiding content.
- Measure the isolated slice on representative desktop and mobile conditions. Keep the fallback when full fidelity is unavailable.
- Ask `cinematic-motion` to own narrative motion and performance trade-offs. Ask `reference-intelligence` only when supplied references create a genuine visual question. Canvas UI owns component selection and implementation readiness, not brand direction or reference translation.

It contains the dated source record, selection matrix, fallback rules, and proof required for a vertical slice.

## OUTPUT SHAPE

**Decision:** visual job -> alternatives compared -> selected or rejected route -> reason -> fallback -> approval boundary.

**Implementation plan:** component family -> contained surface -> semantic DOM structure -> lifecycle/performance controls -> mobile/reduced-motion behaviour -> source/import request -> slice verification.

**Audit:** visual purpose -> source and licence status -> browser/fallback status -> interaction/accessibility -> lifecycle/performance evidence -> required fixes.

## NON-NEGOTIABLE CHECKLIST

1. A named visual job justifies the effect.
2. Still, DOM/CSS, and media alternatives were considered.
3. Semantic content and primary interaction work without the enhanced effect.
4. Browser, mobile, reduced-motion, lifecycle, and performance fallbacks exist.
5. The upstream source, licence, and import method are freshly verified.
6. Approval precedes every external or dependency mutation.
7. One representative slice passes before broader adoption.
