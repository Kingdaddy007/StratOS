# One-Shot Prompt And Intake

## Purpose

Use this reference to start a private spatial prospect-site sprint with the smallest truthful input packet. Ask for missing information only when it can materially change the concept, authority boundary, or implementation.

## Minimum Input Packet

Require or discover these five inputs:

| Input | Minimum | Safe Default |
| --- | --- | --- |
| Prospect | Brand name and category | Derive only from supplied/public evidence; mark uncertainty |
| Evidence | Supplied files, URLs, screenshots, recordings, or research notes | Use only evidence already provided or explicitly authorised for inspection |
| Assets | Image/video/logo/font paths or an asset folder | Inventory what exists; never manufacture missing proof |
| Workspace | Repository/project path and current implementation | Preserve the current stack and accepted strengths |
| Authority | What local changes and checks are authorised | Private local edits only; no dependency install, generation spend, deploy, publish, upload, or sending |
| Sprint mode | `asset-ready` or `media-production` | Use `asset-ready`; select media production only with explicit provider, upload, rights, and budget authority |

Useful but optional:

- desired perception shift or outreach thesis;
- target audience and inquiry posture;
- deadline or run budget;
- known references and what question each should answer;
- must-keep or must-avoid decisions;
- technical constraints, hosting target, or performance budget;
- earlier site fingerprints to avoid repeating.

Do not force the user to complete a long questionnaire when repository truth and supplied evidence answer the decision.

## Copy-Paste One-Shot Prompt

Replace bracketed values. Delete optional lines that do not apply.

```text
Use $spatial-outreach-site-sprint.

Build a private speculative website concept for [PROSPECT / BRAND] in [REPOSITORY OR PROJECT PATH]. Treat this as one autonomous first-pass production sprint, not as a promise that the first generation is final.

Sprint mode: asset-ready.

Evidence to inspect:
- [PUBLIC OR SUPPLIED SOURCE]
- [RESEARCH / SCREENSHOT / RECORDING / EXISTING PORTFOLIO]

Assets:
- [ASSET FOLDER OR FILE PATHS]

Earlier site fingerprints or projects to avoid repeating:
- [OPTIONAL FINGERPRINT FILE OR PRIOR PROJECT PATHS]

The opportunity I want the concept to test is: [OBSERVED CONDITION OR PERCEPTION SHIFT]. If this is not well supported, correct it from the evidence and label the uncertainty.

Authority:
- You may inspect the supplied evidence, edit the local project, make reversible creative and implementation decisions, run the local app, and verify it in the browser.
- Preserve the existing stack and accepted strengths.
- Do not install dependencies, import unapproved third-party source, spend generation credits, deploy, publish, upload prospect assets, or send outreach.
- You may delegate only after the shared thesis and blueprint exist. Suitable disjoint lanes are evidence/asset inventory, bounded asset preparation, one isolated living-continuity prototype, and independent browser QA. Do not distribute page sections before the common system exists.

Run the private speculative sprint lane:
1. Separate `FACT`, `REPORTED`, `INFERENCE`, and `UNKNOWN`. Inventory the real assets and proof.
2. Define one prospect-specific outreach thesis, desired revaluation, visual thesis, proof spine, and honest limit.
3. Generate three lightweight but structurally different whole-page territories, including a restrained option unless the evidence rules it out. For each territory define a different living continuity system that remains perceptible across at least three chapters. Select one using the Master Design Director gates and record the rejected options plus reversal condition.
4. Treat living continuity as the signature principle, not one repeated visual effect. Compare still/image compositing, type, CSS/DOM, SVG, pre-rendered media, persistent objects, and Canvas/WebGL. Use Canvas/WebGL only if it wins for a named continuity job, with semantic, mobile, and reduced-motion fallbacks. Reject any candidate that repeats an earlier site's dominant geometry, opening event, lighting language, reveal pattern, transition behaviour, motion curve, chapter order, or remembered peak.
5. Prototype the most dangerous assumption and one representative vertical slice first. Expand only if the verdict is expand; otherwise revise, simplify, or return to concept.
6. After the brief names reference questions, use the local Design-Audit library only as a candidate pool. Load the smallest relevant reports and record KEEP, ADAPT, REJECT, DEFER, and what is intentionally not copied.
7. Build the complete authored sequence with real content and assets. Motion must reveal hierarchy, space, material, transformation, or proof; remove decorative motion and generic luxury language.
8. Inspect the running page as one cold scroll. Correct the highest-leverage Must Fix issues without redesigning accepted strengths.
9. Verify desktop, mobile, reduced motion, keyboard/focus behavior where applicable, overflow, assets/media, console health, relevant tests, and the production build.

Finish with the sprint thesis, selected direction and rejected alternatives, changed files, Must/Should/Could verdict, evidence actually run, intentionally omitted scope, and residual uncertainty. Do not deploy or send anything.
```

## Asset-Light Variant

When available assets are weak or sparse:

- Design around honest curation, type, crop discipline, sequencing, detail, and selective proof.
- Reduce the number of chapters before repeating one asset as false breadth.
- Use abstract material or DOM treatments only when they support the thesis and do not impersonate missing project work.
- Stop before generated imagery or video. Produce an asset directive and obtain separate approval for any provider, upload, credit spend, or public-use decision.

## Media-Production Variant

Use [media-production-mode.md](media-production-mode.md) when image enhancement or source-image-led video must happen in the same run. The asset-ready prompt above intentionally does not grant provider, upload, or spending authority.

## Existing-Site Variant

When an implementation already exists:

- Audit the live whole first.
- Preserve accepted strengths and identify the fewest structural corrections.
- Use the existing visual thesis when it is coherent; do not manufacture novelty for its own sake.
- Prefer root fixes for responsive layout and motion behavior. Avoid page-wide overflow clipping or decorative layers that can break sticky composition.

## Completion Rule

Call the sprint complete only when the private local artifact works for the verified scope and the handoff identifies what still needs human judgment. A polished screenshot, passing build, or attractive hero alone is incomplete.
