# Decision-Fit Deck Frameworks

Load this reference only when a deck is the appropriate format. Start with the decision, not a slide count. A five-minute decision, a buyer review, a technical evaluation, and a procurement response need different content and evidence.

## Choose a Content Map

Select only the modules needed. A complete deck is not automatically better.

| Module | Use when | Evidence requirement |
| --- | --- | --- |
| Decision and next action | Always | State the decision, owner, timing, and approval status. |
| Buyer context or problem | The buyer's context is known | Attribute buyer statements; label unverified inferences. |
| Current approach and constraint | A change decision needs comparison with status quo | Separate observed facts from a working hypothesis. |
| Capability or proposed approach | Explaining what can be delivered now | State scope, dependencies, exclusions, and version/availability limits. |
| Demonstration or workflow | A buyer needs to see how work happens | Use safe data; label mock or staged behaviour. |
| Proof | Relevant proof exists | Preserve source, date, scope, permission, and comparability. |
| Value scenario | A financial or operational decision needs one | Show inputs, formula, range, omitted factors, and non-guarantee label. |
| Delivery, implementation, or risk | The buyer needs to assess feasibility | State conditions and responsibilities; do not invent a timeline. |
| Commercial terms | The owner approves inclusion | State prices, assumptions, exclusions, and terms within authority. |
| Next action | The decision is ready to move | Make the action specific and achievable. |

## Structure the Narrative

1. State what decision the deck supports and what the audience needs to decide.
2. Present only decision-relevant context. Use the buyer's own wording when it is attributed.
3. Explain the offer or option, including limits and dependencies.
4. Add proof or a labelled scenario only when it improves the decision.
5. Surface trade-offs, open questions, and required approval.
6. End with one clear next action.

## Audience Adaptation

Use role, persona, and jobs-to-be-done material as a starting hypothesis. Do not treat it as an individual's motive or authority. Ask or validate what matters to the actual buyer.

- For a technical review, show supported capability, architecture limits, integration facts, security status, and open questions.
- For a commercial review, show scope, decision consequences, cost conditions, assumptions, and approval gaps.
- For a champion, provide a concise, attributable summary they can accurately relay.

## Final Review

Check the rendered deck, not only the source copy. A visual, chart scale, logo, headline, layout, or fine-print qualification can create a claim stronger than the written text. Confirm that the deck's proof, price, claims, and call to action match the approval record.
